# Reference karst networks and their reference metrics

## What is here

Two published karst networks, and one JSON document per network holding the topology metrics
that the reference implementation of the published method computes for it.

| File | What it is |
|---|---|
| `Huttes_nodes.dat`, `Huttes_links.dat` | The Huttes network: 41 stations, 41 shots, one component, no looping branch |
| `Sakany_nodes.dat`, `Sakany_links.dat` | The Sakany network: 1716 stations, 1784 shots, one component, 16 looping branches |
| `huttes.golden.json`, `sakany.golden.json` | The reference metrics for each, regenerated by `scripts/karstnet-oracle.mjs` |

The `_nodes.dat` file is a three-column XYZ matrix, one row per station; the `_links.dat` file
is the edge list over those row numbers.

## Why both

Huttes is small enough to reason about by hand and has no looping branch, so every metric on it
is defined. Sakany is two orders of magnitude larger and does have looping branches, whose
tortuosity is undefined and which the published method excludes from the mean while counting
them — a path that a small clean network never reaches and that is easy to get silently wrong.

## The point of committing the metrics beside the networks

The reference implementation is Python. It is a developer and CI tool here, never a runtime
dependency and never on a request path. Committing its output means the .NET suite proves the
metrics against the reference arithmetic on a machine with no Python installed at all: a broken
reference install degrades the gate that verifies the goldens, not the test suite that uses them.

A regeneration or a drift check costs about 30 seconds of wall clock, nearly all of it
installing the pinned packages; the measurement itself is milliseconds on Huttes and a fraction
of a second on Sakany. Baking the pinned install into a local image once would remove most of
that, and is worth doing only if the check starts running often enough to notice.

Regenerate with `node scripts/karstnet-oracle.mjs`; verify the committed values still agree with
`node scripts/karstnet-oracle.mjs --check`. Both pin the interpreter, the reference library and
every transitive package, because a metric that changes quietly with a dependency upgrade is
worse than one that fails to install.
